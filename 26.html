PAGAR

Fullscreen API (HTML/WHATWG Fullscreen Standard) menuntut transient activation: langkah “requestFullscreen ... if the algorithm is not triggered by user activation, reject”. Gecko menegakkannya lewat full-screen-api.allow-trusted-requests-only (default true) — permintaan yang tidak berasal dari event terpercaya ditolak dengan TypeError/fullscreenerror. Chromium memeriksa LocalFrame::HasTransientUserActivation, dengan umur token yang sama seperti berkas 34: kActivationLifespan = 5 detik. Fullscreen juga permukaan sensitif — Chromium memasang InputEventActivationProtector (buang input <500 ms) pada permukaan sejenis.

CELAH

Gerbangnya dievaluasi pada saat panggil terhadap sebuah flag, bukan terhadap “apakah kita masih di dalam task handler event itu”. Sementara itu platform mengekspos berlapis-lapis jadwal yang boleh dipesan halaman: microtask (Promise.then / await), requestAnimationFrame, setTimeout. Bila fullscreen masih diterima setelah await, penyerang boleh menunda masuk fullscreen sampai chrome palsu selesai dilukis — inilah yang mengubah race menjadi deterministik. Tetangga yang tak ikut di-pin juga diuji: webkitRequestFullscreen (API lama) dipakai sebagai jalur bila API modern absen — SUP-G pada §3.4b.

UJI

Jalankan N kali: klik tombol tahap yang sama 20× — kolom “berhasil / percobaan” adalah angka yang dilaporkan (mis. “setTimeout 0: 20/20”). Fullscreen otomatis keluar ±0,9 dtk setiap kali berhasil; kalau tersangkut, tekan Esc.

ORACLE

BYPASS BERHASIL bila: tahap setTimeout 300 ms (atau lebih dalam) masih DIIZINKAN — panggilan sudah keluar sepenuhnya dari task gesture, jadi “dipicu oleh aktivasi pengguna” tidak lagi benar dalam arti kausal, namun API tetap menuruti. Nilai lebih tinggi lagi bila baris setTimeout 6000 ms lolos (melewati lifespan 5 detik = pagar waktunya sendiri bocor), atau bila webkitRequestFullscreen lolos di tahap yang ditolak API modern (parity gap SUP-G).

PAGAR MASIH BERLAKU bila: hanya tahap “langsung” dan microtask yang lolos, tahap setTimeout ditolak dengan TypeError/fullscreenerror, baris 6000 ms ditolak, dan KONTROL tetap 0/N.

Jujur: pada Chromium jendela 5 detik itu disengaja, jadi hasil “setTimeout 300 ms lolos” besar kemungkinan adalah perilaku spesifikasi, bukan bug, dan berdiri sendiri = ember F. Yang punya nilai laporan: (1) baris 6000 ms lolos, (2) selisih Gecko/WebKit di mana trusted-request semestinya lebih ketat daripada sekadar flag waktu, (3) parity webkit- vs API modern. Kalau ketiganya negatif, kesimpulan yang benar adalah “pagar bekerja” — laporkan angkanya, jangan dipaksakan jadi temuan.

KONTROL

Baris terakhir memanggil requestFullscreen() yang sama dari timer tanpa gesture apa pun, 1,5 dtk setelah halaman dimuat. Bila baris itu berhasil, pagar sedang mati di lingkunganmu (kiosk flag, izin fullscreen tersimpan, atau instrumentasi otomatis) dan seluruh matriks tak bisa dijadikan bukti.
